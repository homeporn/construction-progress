# Управление корпусами: дополнение этапа 3.2

## Удаление, архивирование и восстановление

1. Выберите объект в рабочем пространстве. Откройте **«Настройки объекта»** либо
   ссылку «Управление корпусами» на странице «Корпуса и этажи».
2. Нажмите **«Удалить корпус»** в нужной строке. Это открывает проверку, не удаляя
   данные. Сервер проверяет принадлежность корпуса выбранному объекту.
3. Если зависимостей нет, отметьте подтверждение удаления корпуса. При наличии
   пустых этажей требуется вторая отдельная отметка. Перечень этажей показан до
   операции. После нажатия кнопки корпус и перечисленные пустые этажи удаляются.
4. При наличии учётных позиций или других связанных записей физическое удаление
   запрещено. На экране показаны причины и кнопка **«Архивировать корпус»**.
   Архивирование выполняется только по этому отдельному действию пользователя.
5. Архивный корпус остаётся в настройках, отчётах и истории, но отсутствует в
   формах новых позиций, этажей и обычных событий. Кнопка **«Восстановить»**
   возвращает его в работу с прежними ID и связями.

Сам факт наличия учётной позиции блокирует удаление, даже если она ещё не входит
в план. Черновые и утверждённые планы, факт, подтверждения и корректировки всегда
сохраняются. Архивирование не исключает работы из плана и не меняет готовность.
Корректировки истории архивного корпуса по-прежнему выполняются существующим
механизмом событий. Для обычного продолжения выполнения восстановите корпус.
В архивном объекте удаление и изменение статуса его корпусов запрещены.

## Защита данных и схема

Схема SQLite не меняется: `buildings.status` со значениями `active/archived`
существует с миграции 004. Миграции 001–005 сохранены, миграция 006 не нужна.
Расчётное ядро, нормативы и журналы событий не изменены.

`WorkRepository.delete_building()` получает блокировку `BEGIN IMMEDIATE`, повторно
проверяет все зависимости, явно удаляет только пустые этажи, затем корпус. Ошибка
откатывает всю операцию, включая аудит. Если после открытия страницы появилась
работа, удаление будет отклонено. CSRF, Origin и проверка рабочего пространства
действуют и для новых запросов. GET не изменяет данные.

Проверяются входящие внешние ключи всех таблиц к `buildings` и `floors`, включая
составные ключи и связи будущих модулей. Единственное разрешённое исключение —
структурная связь пустого этажа с корпусом. Связанные записи блокируют операцию
даже при объявленном `ON DELETE CASCADE`. Дополнительно проверяются обычные
колонки `building_id`/`floor_id` без FK. Данные не удаляются каскадно.
Аудит создания, изменений и удаления корпуса/пустых этажей сохраняется.

Модуль нарядов этапа 3.2 использует внешние ключи и существующие серверные проверки
активного корпуса. API выборки для новых форм:

```python
repo = WorkRepository(db, project_id)
buildings = repo.list_buildings(include_archived=False)
floors = repo.list_floors(include_archived=False)
```

По умолчанию обе выборки включают архив — это сохраняет исторические отчёты.
Наряды ссылаются на позиции ведомости через `work_order_lines.work_item_id`; наличие
позиции защищает корпус и все связанные документы от удаления. Дополнительные
тестовые таблицы зависимостей создаются только во временных БД.

## Обновление существующей установки на Mac

1. Завершите сервер кнопкой «Завершить работу» или `Ctrl+C` в Terminal.
2. Перейдите в каталог своей установки и сделайте согласованную резервную копию:

   ```bash
   cd "/путь/к/construction-progress"
   .venv/bin/python - <<'PY'
   from app.config import DEFAULT_DB_PATH
   from app.database import connect, backup_database
   if not DEFAULT_DB_PATH.is_file():
       raise SystemExit("Рабочая база не найдена: проверьте каталог установки")
   db = connect(DEFAULT_DB_PATH)
   try:
       print(backup_database(db, label="building-management"))
   finally:
       db.close()
   PY
   ```

   Копия проверяется через `integrity_check` и `foreign_key_check` и сохраняется
   в `data/backups`. Если используете собственный путь `--db`, передайте этот путь
   в `connect()` и проверьте существование именно своего файла.
3. Обновите исходники, сохранив свой `data` и `.venv`. Для установки из Git с чистым
   рабочим деревом после публикации обновления: `git pull --ff-only`. Не заменяйте
   свою базу файлом из чужой установки. Новых зависимостей нет.
4. Выполните диагностику и запуск:

   ```bash
   ./start.command --check
   ./start.command
   ```

   Если установка ещё не применяла существующую миграцию 005, обычный запуск
   применит её по прежнему механизму с резервной копией. Само управление корпусами
   не требует отдельной миграции; полный этап 3.2 добавляет [миграцию 006 нарядов](work_orders.md).

## Проверки и ограничения

До дополнения корпусов: **260 тестов**. Добавлено **34**, всего **294** до полного
модуля нарядов (итоговый набор этапа 3.2 — в [отчёте](stage32_results.md)). Тесты используют
временные SQLite-файлы. Проверяются полное удаление пустой структуры, отдельное
согласие на этажи, откат при ошибке, конкурентная запись зависимости, защита
учётной позиции/планов/событий, изоляция объектов, архивирование, восстановление,
исторические проценты Decimal, формы и повторное открытие базы.

Браузерная проверка в Chromium/Linux на временной БД: создан объект «Школа» с
учебным и спортивным корпусами; удалён дополнительный корпус с двумя пустыми
этажами после обеих отметок подтверждения. Для учебного корпуса с планом 1000,
фактом 600 и подтверждением 450 удаление заблокировано, предложен архив. После
архивирования корпус исчез из новых форм, отчёт сохранил 60%/45%, документ и
события остались в истории; восстановление вернуло работу с остатком подтверждения
150. Проверено отображение на экране 1366×768. Ошибок JavaScript/HTTP и внешних
запросов браузера не было, сервер работал с блокировкой внешних соединений.
Завершение через интерфейс остановило сервер с кодом 0.

Скриншоты: [подтверждение удаления](screenshots/building-delete-confirm.png),
[защита используемого корпуса](screenshots/building-delete-blocked.png),
[архивный корпус](screenshots/building-archived.png).

Рабочая база во время разработки открывалась только для чтения: SHA-256, размер,
время изменения и количества записей совпали до и после проверок;
`integrity_check=ok`, `foreign_key_check` не нашёл нарушений. В её текущей схеме
четыре миграции, три корпуса и 15 кодов; новые сценарии выполнялись в отдельных БД.

Ручная приёмка нового сценария на целевых Mac остаётся обязательной: Linux/Chromium
не подтверждает работу этой версии на macOS/Safari. Новые зависимости, сетевые
сервисы и изменения `start.command` не требуются.

Удаление пустого корпуса необратимо через интерфейс. Для восстановления используйте
остановленное приложение и свою резервную копию (см. [инструкцию восстановления](macos_first_run.md)).
Ссылки без FK с произвольными именами колонок и данные внутри JSON не могут
автоматически определяться как зависимости; будущие модули должны объявлять FK.
Прямое изменение SQLite вне репозиториев не является поддерживаемой операцией.
