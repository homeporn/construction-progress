# Ведомость → факт → подтверждение — этап 3.1.1

Все экраны используют одну позицию `work_item_id`. Отдельных копий работ или таблиц
очереди нет. Кодификатор и нормативно-весовая модель остались прежними.

## Работа в интерфейсе

1. Выберите объект, добавьте этаж и учётную позицию в ведомость. Заполните план и
   собственную норму, утвердите версию. Работа из одного черновика для факта недоступна.
2. Откройте «Фактическое выполнение». Таблица показывает план, накопительный факт,
   подтверждение и остаток по плану в единицах позиции. Фильтры: корпус, этаж,
   конструктивный элемент, вид работ. Нажмите «Добавить факт» у нужной строки.
3. Укажите дату и объём. Каждый ввод добавляет отдельную дельту; +200 и +400 дают
   накопленные 600, сохраняя оба события. Полный факт выше плана также сохраняется.
4. В «Подтверждении» автоматически появляются работы с положительной разностью
   факта и подтверждения. Нажмите «Подтвердить объём»: форма выберет работу и покажет
   доступный остаток. Сам объём не заполняется — введите его самостоятельно и
   укажите дату, документ-основание и, при необходимости, комментарий.
5. При факте 600 подтверждения 450, 100 и 50 оставляют соответственно 150, 50 и 0.
   Полностью принятая работа исчезает из вкладки «Ожидают подтверждения», оставаясь
   во вкладке «Все работы» и в журнале. Новый факт +100 возвращает её в ожидающие.

«Все работы» содержит позиции выбранной версии с зарегистрированным фактом на
дату среза, включая полностью принятые и работы с нулевым итогом после исправлений.
Факт выше плана не обрезается при вычислении неподтверждённого остатка: при плане
100 и факте 115 доступны к подтверждению 115, хотя физическая готовность ограничена 100%.

Источник новых событий из интерфейса — «Ручной ввод». Корректировка — отдельное
событие со ссылкой на исходное. Для полностью принятой или исключённой работы
используйте ссылку «Корректировать историю, включая исключённые работы».
Старые события не удаляются и не заменяются суммарными значениями.

## Версия и исторический срез

По умолчанию выбраны текущий день UTC, текущий момент знаний и действующая
утверждённая версия выбранного объекта/направления. В фильтрах можно выбрать другую
версию, дату и отсечение знаний в ISO-формате с часовым поясом. Пустое поле отсечения
означает «сейчас»; фактически использованный момент отображается над таблицей.

Факт учитывается по дате выполнения и регистрации, подтверждение — по дате
подтверждения и регистрации. Поздние события не попадают в ранний срез знаний.
Если на 17-е факт 600 и подтверждение 450, а 18-го добавлено подтверждение 100,
срез 17-го продолжает показывать остаток 150; срез 18-го показывает 50.

Прошлые срезы, фиксированное отсечение знаний и прежние версии доступны для
просмотра. Для нового обычного события вернитесь в текущий рабочий срез. При этом
в форме можно указать прежнюю дату события: доступный объём проверяется именно
на эту дату, а дата регистрации назначается текущим моментом. Даты в будущем запрещены.
Показанный до сохранения остаток может измениться из-за другой записи; при сохранении
сервер получает блокировку записи и пересчитывает его заново.

Состав очереди ограничен выбранным планом. Исключённые работы остаются в журналах;
их старую версию можно просмотреть отдельно. Прежняя проверка MISSING_PLAN_LINE
сохранена: видимые события вне состава выбранного плана делают его общий отчёт INVALID.

## Надёжность и хранение

- Количества сохраняются каноническими Decimal TEXT. Суммы и разность вычисляются
  точной арифметикой Python; SQLite REAL/SUM(TEXT) и арифметика JavaScript не применяются.
- Историческое ядро и проверка доступного остатка используют общий запрос журналов
  `EventRepository.cumulative_quantities()`, с обязательной областью объекта.
- Формулы трудоёмкости, весов, освоения и остатка по плану не менялись. Таблица
  получает их из существующего ядра; очередь добавляет только `actual - confirmed`.
- Обычный объём положителен, нулевые события запрещены. Перед подтверждением под
  `BEGIN IMMEDIATE` проверяются факт/подтверждение на выбранную дату, актуальность
  плана и принадлежность позиции. Затем проверяется вся историческая сетка границ
  бизнес-дат и времени знаний, как и раньше. Ошибка откатывает запись вместе с аудитом.
- Две независимые операции не могут подтвердить один остаток дважды. Повторная
  отправка одной формы с тем же `event_key` также не создаёт событие.
- `source_type` хранит происхождение в обоих существующих журналах. Новые ручные
  события получают `manual`, прежние — `legacy`, поскольку их источник не был записан.
  Источник включён в аудит. Доверенный Python API может указать иной идентификатор
  источника; наличие наряда не требуется. Модуля нарядов на этом этапе нет.

## Обновление на macOS

По сообщению пользователя, версия 3.1 проверена на macOS Monterey в Safari.
Версия 3.1.1 проверена в Linux/Chromium и требует повторной приёмки на Mac.
Python, Flask и прочие зафиксированные зависимости не изменились.

1. Завершите старый сервер через меню приложения или Ctrl+C.
2. Сохраните копию старой установки. Обновите исходники, не заменяя `data`, `.venv`
   и `.git`. Команды копирования с сохранением каталогов приведены в [workspaces.md](workspaces.md).
3. Из Terminal в каталоге установки выполните:

```bash
chmod u+x start.command
./start.command --check
./start.command
```

Диагностика ничего не мигрирует. При первом обычном запуске существующей схемы 004
создаётся согласованная копия через SQLite Backup API:
`data/backups/before-event-flow-<UTC>-<идентификатор>.sqlite3`.
Копия проверяется, затем 005 в одной транзакции добавляет `source_type` двум журналам
и обновляет только триггеры аудита вставки. Таблицы не пересоздаются, ID, даты,
объёмы, нормативы, версии и старый аудит сохраняются. При ошибке транзакция откатывается,
копия остаётся. Повторный запуск 005 пропускает. Порядок восстановления через Backup API
описан в [workspaces.md](workspaces.md#восстановление-после-ошибки); выберите файл
`before-event-flow-…sqlite3` и при полном откате верните прежние исходники.

Для приёмки отдельно от рабочей базы:

```bash
./start.command --check --test-db
./start.command --test-db
```

Установка новых пакетов не нужна; подготовленное приложение работает офлайн.

## Ограничения

- Исторические срезы и прежние версии открываются для просмотра; новые обычные
  события регистрируются из текущего плана. Регистрация задней датой сохраняет
  текущий момент знаний и не переписывает старые срезы.
- Доступный остаток в форме относится к показанной дате среза. Если изменить дату
  подтверждения, сервер использует эту дату при сохранении и сообщит об ином лимите.
- Подтверждение — объёмное событие с документом, а не отдельное подписание отчёта.
  Журналы остаются без пагинации, проверка всех исторических границ требует
  профилирования на больших объёмах. Приложение рассчитано на локальную работу.
