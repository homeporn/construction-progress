## 2. Методика и ограничения достоверности

- Три профиля создаются отдельным генератором; seed **421**. Назначение — новый
  абсолютный `.sqlite3` внутри временного каталога ОС вне проекта. Существующий
  файл, ссылка на файл и рабочий каталог отклоняются; SQLite-файл создаётся с
  `O_EXCL`. Ошибочная генерация не удаляет свой частичный файл автоматически.
- Генерация сохраняет FK и триггеры. Планы и события массово заполняются SQL
  только внутри синтетического стенда; организации, работники, бригады, наряды,
  группы и утверждения используют имеющиеся репозитории. Нормы в стенде — явно
  учебные значения, не нормативная база строительства.
- Измерения читают исходную нагрузочную базу и создают согласованную временную
  копию через SQLite Backup API. Рабочая база приложения не используется.
- Серверные экраны измеряются Flask test client; это время Python/SQLite/Jinja2
  без браузерной отрисовки и сетевого обмена. Импорт Excel измеряется реальным
  сервисом импорта, не прямым INSERT работников.
- Два подготовительных вызова операции, затем **10 замеров**. Если первый вызов
  дороже 10 секунд — **3 замера** с явной отметкой в JSON. p95 — nearest-rank;
  при 10 повторах он совпадает с максимумом. Трёх повторов недостаточно для
  устойчивой оценки хвоста распределения; их p95 фактически максимум трёх.
- `cold_app_start_seconds` — создание Flask app в уже запущенном Python, после
  импортов и копирования БД. `cold_operation_seconds` — первый вызов сценария.
  Это не запуск Python с нуля и не гарантированно холодный файловый кэш ОС.
- SQL — количество вызовов sqlite trace callback, включая PRAGMA, управление
  транзакциями и возможные повторные вызовы из триггеров. Это не физические
  чтения страниц и не число уникальных SQL-запросов. Трассировка добавляет накладные расходы.
- RAM — `ru_maxrss`: верхняя отметка **всего процесса**, включая подготовку и
  предыдущие операции серии. Это не прирост/отдельный пик каждой операции.
- Исходная версия фиксирована снимком, но оптимизации добавлялись между сериями
  «после». Единого финального коммита и единой изолированной серии на нём нет.
  Основные `after-*.json` и дополнительные `journals-final-*.json`,
  `after-small-final.json` относятся к разным проходам; ниже они разделены.
- Дополнительные серии частично совпали с другой нагрузкой в общей среде.
  Особенно заметны ухудшения `after-small-final.json` и среднего журнала.
  Они приведены без отбрасывания. Причина каждой разницы не изолирована;
  нельзя приписывать её целиком коду или считать показанные проценты гарантией.

Состав/ID/числовые значения стенда воспроизводятся seed. Полный бинарный файл
не обязан иметь одинаковый SHA: часть дат создания/аудита формируется репозиториями
по текущему времени. Сопроводительные JSON содержат реальные размеры и параметры
созданных здесь файлов.

## 3. Среда

Linux x86_64, CPython **3.13.5**, SQLite **3.46.1**, Flask 3.1.3,
`Linux-6.18.55-x86_64-with-glibc2.41`. CPU — AMD EPYC 9V74; процесс видит
3 логических CPU, квота контейнера — 2 CPU. Видимая RAM 10 452 471 808 байт
(около 9,73 GiB), лимит контейнера — 8 GiB. Среда общая, не выделенный стенд.

Браузерная серия — отдельный Linux/Chromium; Python браузерного драйвера не
используется для серверной статистики. macOS/Safari в этой попытке не проверялись.
Результаты Linux не являются прогнозом скорости Catalina или другого Mac.

В стендах есть два направления, две версии плана, разные коды/единицы, учебные
нормы, поздняя регистрация, отрицательные корректировки факта, частичное выполнение,
перевыполнение, неподтверждённый факт, архивный корпус, персонал без бригад,
выданные наряды без автоматического создания объёмов и утверждённые табели.
Один работник принадлежит одному подрядчику; в этих трёх профилях персонал
распределён по объектам. Генерация общего работника на нескольких объектах,
версий состава групп и исторических корректирующих версий табеля **не добавлена**.
Их поведение покрывается прежними регрессионными тестами, а не этими нагрузочными стендами.

Основная серия каждого профиля измеряет **первый объект/подрядчика**, не объединяет
независимые объекты. Поэтому крупная база содержит 50 000 позиций и 2 000 людей,
но основной отчёт объекта имеет около 10 000 позиций и табель около 400 людей.
Для табелей ровно на 500 и 2 000 работников есть отдельные дополнительные серии.

## 6. Узкие места и сделанные изменения

1. `AnalyticsService.build()` раньше формировал дневную динамику даже для
   сводки, где график не выводится. Добавлен `include_series`; страницы без
   графика пропускают эту работу. API по умолчанию и Excel сохраняют полный расчёт.
   Формулы физического прогресса не менялись.
2. Последняя дата события в аналитике раньше находилась через получение двух
   полных журналов с метаданными. Добавлен `latest_recorded_at`: SQL MAX времени
   с отбором по проверенным ID, проекту, бизнес-дате и отсечению знаний. ID
   разбиваются на блоки по 900. Decimal-объёмы в SQL не суммируются.
3. Появилась пагинация отображаемых списков по 50 строк в ведомости, очередях
   факта/подтверждения, персонале, табеле и части аналитики. Глобальные итоги
   и экспорт не считают только показанную страницу.
4. Для истории событий добавлены фильтры SQL, COUNT и LIMIT/OFFSET; порядок
   `recorded_at DESC, id DESC` сохранён. В остальных частях пагинация в основном
   ограничивает HTML после получения полной выборки — это **не полноценная
   серверная SQL-пагинация всего приложения**.
5. Для ручного выбора работников массового заполнения добавлено сохранение
   выбранных ID между страницами в sessionStorage. Серверные проверки остались.
   Повторная браузерная проверка последней версии этого JS не выполнена.
6. В тестовом генераторе Excel `book()` стабилизированы служебные даты ZIP.
   Это исправление фикстуры, не механизма импорта и не логики идентификации людей.

Долгоживущий кэш, материализация фактических объёмов, SQL REAL/SUM(TEXT), новые
зависимости, облачные сервисы, смена режима SQLite и новые бизнес-функции не вводились.

Оставшиеся причины задержек: полный расчёт выбранного объекта перед частью
фильтров, полные вспомогательные выборки/списки предупреждений, N+1 персонала
и проверок табеля, тяжёлые наборы истории, формирование полного дерева XML XLSX.
Даже при 50 основных строках HTML может оставаться большим из-за вспомогательных
данных/предупреждений. Обоснованных новых индексов по этим данным пока не добавляли.

```sql

SELECT quantity_delta FROM fact_events
WHERE work_item_id=? AND work_date<=? AND recorded_at<=?;
-- SEARCH fact_events USING INDEX idx_fact_events_slice
-- (work_item_id=? AND work_date<?)
```

## 9. Табели и одновременные операции

Отдельные стенды с одним объектом/подрядчиком, без предположения, что распределённый
профиль на 2 000 людей равен табелю одного подрядчика на 2 000:

| ---: | ---: | ---: |
| 500 | 0.3903 / 0.5904 | 127673 |

Запись на приватной копии крупной базы (2 прогрева + 10 повторов):

| Операция | Среднее / p95, с |
| --- | ---: |
| Добавление факта | 0.000555 / 0.000713 |
| Частичное подтверждение | 0.002173 / 0.003131 |

Для этой серии перед записью ячеек создана корректирующая версия; сама операция
создания/передачи/утверждения/массового ввода здесь не измерялась отдельно.
В основном крупном стенде выбранный табель содержит около 400 работников.
Запись новых событий идёт по одной позиции, её история растёт в течение серии;
это не стресс одной позиции с сотнями тысяч событий.

Параллельно выполнено 20 операций четырьмя потоками — добавление факта и чтение
табеля отдельными соединениями. Зафиксировано **0 ошибок, 0 database is locked**.
Это наблюдение на данном стенде, не гарантия отсутствия блокировок. Параллельные
экспорт/подтверждение/массовая запись отдельной нагрузочной серией не проверены.
Проверены настройки: `busy_timeout=5000`, `journal_mode=delete`, `foreign_keys=1`.
Режим SQLite не менялся.

## 10. Корректность и регрессия

Сохранённые пары `equivalence-before-*.json` / `equivalence-after-*.json` совпали:
**17 + 47 + 77 = 141 проекция**, расхождений нет. Включены обе дисциплины,
две версии плана, разные бизнес-даты/отсечения знаний, поздние корректировки,
аналитика, состав существующих групп, текущие утверждённые табели и логическое
содержимое Excel первого объекта. Для Excel сравниваются ячейки/типы/стили/
значения; служебные ZIP-даты не сравниваются. Время формирования табеля фиксируется
при сравнении. Это проверка данного набора, не доказательство всех возможных случаев.

| Прогон | Фактический результат |
| --- | --- |
| Чистый исходный 4.2 после перезапуска | **823 passed**, 84,50 с |
| Промежуточный полный после первых изменений и 5 новых тестов | **828 passed**, 93,71 с |

| Полный прогон после исправления фикстуры | **Не выполнялся** |

Сбой: `test_saved_mapping_links_same_canonical_employee_on_another_shared_project`.
Фикстура генерировала якобы тот же XLSX дважды; ZIP записывал текущее время.
Два логически одинаковых файла могли иметь разные байты/SHA при переходе
границы времени ZIP и не считались одним файлом импорта. Это воспроизведено
с двумя контролируемыми ZIP-временами: содержимое частей одинаково, байты различны.
Фикстура `book()` получила фиксированные ZIP-даты; продуктовая логика осталась
прежней. Зелёный модуль из 49 тестов не заменяет полный финальный прогон.

Шесть новых обычных тестов проверяют защиту пути/перезаписи, определение p95,
целостность и допустимость событий генератора, эквивалентность скрытого графика,
пагинацию/фильтры и порядок/COUNT/изоляцию SQL-журнала. В них нет жёстких
временных порогов. Нагрузочные инструменты запускаются отдельно от pytest.

### Команды для повторной проверки на Mac

Остановите старое приложение; обновляйте код, сохраняя свою `data/` и `.venv`.
Новых runtime-зависимостей нет. Оптимизации не требуют новой миграции; если
установка ещё не на схеме 010, применяются прежние механизмы обновления/Backup API.
Сначала проверьте `./start.command --check`; для функциональной приёмки —
`./start.command --test-db`. Этапы 4.1/4.2/4.2.1 требуют отдельной приёмки Safari.

```bash
cd "/путь/к/construction-progress"
.venv/bin/python -m pytest -q
.venv/bin/python -m pytest tests/performance -q

PERF_DIR=$(mktemp -d "${TMPDIR:-/tmp}/cp421.XXXXXX")
.venv/bin/python tools/performance/generate_dataset.py --output "$PERF_DIR/small.sqlite3" --profile small
.venv/bin/python tools/performance/benchmark.py --db "$PERF_DIR/small.sqlite3" --output "$PERF_DIR/mac-small.json"
# Затем, по ресурсам устройства, medium и large с НОВЫМИ именами файлов.
```

Генератор не перезаписывает существующие файлы. Нагрузочная БД не является рабочей
БД и не должна переноситься поверх `data/construction_progress.sqlite3`.

Для повторения исходной серии можно распаковать сохранённый снимок в отдельный
временный каталог и передать его через `--code-root`:

```bash
BASELINE_DIR=$(mktemp -d "${TMPDIR:-/tmp}/cp421-before.XXXXXX")
tar -xzf docs/performance/stage42-baseline-source.tar.gz -C "$BASELINE_DIR"
.venv/bin/python tools/performance/benchmark.py --db "$PERF_DIR/small.sqlite3" --code-root "$BASELINE_DIR" --output "$PERF_DIR/mac-before-small.json"
```

На Mac отдельно зафиксируйте `sw_vers`, `uname -m`, Python/SQLite, CPU и RAM.
Не объединяйте новые macOS-значения с Linux-таблицами. Браузерный Python-скрипт
сейчас настроен на Linux `/usr/bin/chromium`; для Safari нужна ручная проверка:
переключение объектов, страницы/фильтры, выбор людей на нескольких страницах,
запись/утверждение/коррекция табеля, полный экспорт, история и отсутствие внешних запросов.

## 12. Сохранность и незавершённые пункты

Рабочая база репозитория не мигрировалась и не использовалась для нагрузки.
SHA-256 и mtime совпадают с началом:

`10f7b9964447ec33eb9d4865ef38b52384f606174217c1304d420510a55dc036`

Повторное чтение: `integrity_check=ok`, `foreign_key_check=[]`. В ней по-прежнему
маркеры 001–004; это файл репозитория, не база пользователя на Mac. Миграции
001–010 не изменены. Ни текущие данные пользователя Mac, ни резервные копии
не открывались для испытаний. Push и этап 4.3 не выполнялись.

Не закрыто к моменту остановки:

- единый полный зелёный прогон финального состояния и финальная браузерная приёмка;
- изолированная повторяемая серия на одном зафиксированном коде без параллельной нагрузки;
- достижение всех целевых времён, в частности большого журнала/фильтра ведомости;
- SQL-пагинация всех вспомогательных данных, предупреждений и истории; полное устранение N+1;
- профилирование cProfile и полные планы самых дорогих SQL, а не один адресный пример;
- отдельные измерения всех операций статусов/массового ввода/импорта табеля;
- сквозной отчёт одного объекта на 50 000 позиций и потоковая оптимизация XLSX;
- нагрузочный общий работник нескольких объектов, версии групп/исторических табелей,
  конкурентное подтверждение/экспорт и большие браузерные профили;
- целевая приёмка на Mac/Safari.

Результат полезен как измеренная отправная точка, но **все критерии этапа 4.2.1
пока не выполнены**. Машинные результаты: [каталог performance](performance/),
[краткий итог](stage421_results.md), [сводный статус](performance/report-status.json).
