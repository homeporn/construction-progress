# Объекты и рабочие пространства — этап 3.1

## Использование

1. Откройте «Объекты → Создать объект».
2. Укажите название «Школа», уникальный код и количество корпусов `2`.
3. Замените предложенные названия на «Учебный» и «Спортивный», задайте их коды.
4. Нажмите «Создать объект и корпуса». Ошибка любой строки отменяет всю операцию.
5. Новый объект сразу выбирается. В его настройках можно менять корпуса, коды,
   названия, порядок, архивировать и восстанавливать корпуса или весь объект.
6. В «Корпуса и этажи» добавьте нужные этажи. Затем создайте учётные позиции,
   черновик плана и введите объёмы с собственными нормативами. Утвердите план.
7. Работы автоматически появятся в «Фактическом выполнении» через `work_item_id`.
   Черновой план не делает работу доступной для нового выполнения.
8. Введите факт и подтверждение; прогресс показан раздельно по СМР/проектированию.
9. Выберите другой объект в боковом меню кнопкой «Выбрать»: старые фильтры и ID
   версии сбрасываются. Вернитесь к школе — её данные сохраняются.

Кодификатор общий, его 15 записей не копируются при создании объекта. Нумерация
планов независима для каждой пары объект/направление. История, отчётные даты и
отсечение знаний действуют внутри выбранного объекта. Переименование корпуса не
меняет его ID. Удаления объектов/корпусов из интерфейса нет: используйте архив.
Архивный объект доступен для чтения; для записи восстановите его. Архив корпуса
не удаляет его вклад в ранее утверждённый план или события.

Фильтры выполнения: объект в меню → корпус → этаж → элемент → вид работ → позиция.
Сервер проверяет принадлежность независимо от JavaScript. Для исправления исключённой
из нового плана работы нажмите «Корректировать историю, включая исключённые работы».
Выберите исходное событие: исправление записывается отдельной дельтой.

## Обновление существующей установки на Mac

Прежнюю версию пользователь уже проверил на macOS; изменения 3.1 требуют повторной
приёмки. Новых Python-зависимостей нет. Интерпретатор и версии зависимостей остаются
указанными в `compatibility.md`; обычный запуск работает без интернета.

1. Завершите старый сервер кнопкой приложения или Ctrl+C. Закрытия вкладки недостаточно.
2. Сохраните копию всей старой папки приложения, включая `data`, вне новой папки.
3. Скопируйте файлы новой версии поверх установки, сохранив `data`, `.venv` и `.git`.
   Например, в Terminal (замените пути на свои; кавычки обязательны для пробелов):

```bash
cp_release="$HOME/Downloads/construction-progress-3.1"
cp_install="$HOME/Applications/Construction Progress"
rsync -a --exclude='data/' --exclude='.venv/' --exclude='.git/' \
  --exclude='__pycache__/' --exclude='.pytest_cache/' \
  "$cp_release/" "$cp_install/"
cd "$cp_install"
chmod u+x start.command
./start.command --check
./start.command
```

`--check` читает SQLite без миграций. Первый обычный запуск создаёт через SQLite
Backup API файл `data/backups/before-projects-<UTC>-<идентификатор>.sqlite3`, проверяет
его `integrity_check` и FK. Затем 004 в одной транзакции создаёт «Строительный проект»
и привязывает старые корпуса и версии к нему. ID и исходные колонки всех учётных
таблиц сравниваются до/после; проверяются все FK и целостность. Старые миграции не
переписываются. Если прежняя база была этапа 1, сначала применяется 003.
При ошибке 004 откатывается; резервная копия сохраняется. При нехватке прав на
создание копии миграция не начинается. Повторный запуск не создаёт дубли.

Если `.venv` отсутствует, выполните явную первоначальную подготовку с интернетом
через `./start.command --prepare` согласно `macos_first_run.md`. Само обновление 3.1
при уже подготовленном окружении не требует `--prepare`.

Для отдельной приёмки без рабочей базы:

```bash
./start.command --check --test-db
./start.command --test-db
```

## Восстановление после ошибки

Остановите все серверы. Сначала устраните указанную причину (права на каталог,
свободное место, блокировку другой копией приложения) и повторите `--check` и запуск.
Не удаляйте рабочую SQLite-базу. Не запускайте старую программу поверх новой схемы.

Для явного отката выберите проверенную копию из `data/backups`. Сохраните текущую
базу отдельно и восстановите выбранную копию через Backup API:

```bash
.venv/bin/python - data/backups/before-projects-ВАША-КОПИЯ.sqlite3 <<'PY'
from pathlib import Path
import sqlite3, sys
from datetime import datetime

source = Path(sys.argv[1]).resolve(strict=True)
working = Path('data/construction_progress.sqlite3').resolve()
saved = working.parent / ('before-restore-' + datetime.now().strftime('%Y%m%d-%H%M%S') + '.sqlite3')
if saved.exists() or source == working:
    raise SystemExit('Выберите другие пути: файлы не перезаписываются')
with sqlite3.connect(source.as_uri() + '?mode=ro', uri=True) as backup:
    assert backup.execute('PRAGMA integrity_check').fetchone()[0] == 'ok'
    assert not backup.execute('PRAGMA foreign_key_check').fetchall()
    with sqlite3.connect(working) as current, sqlite3.connect(saved) as previous:
        current.backup(previous)
        backup.backup(current)
        assert current.execute('PRAGMA integrity_check').fetchone()[0] == 'ok'
        assert not current.execute('PRAGMA foreign_key_check').fetchall()
print('Восстановлено:', source, '\nПрежняя база сохранена:', saved)
PY
```

Для полного возврата к прежней версии восстановите также её исходники из копии,
сохранив восстановленный `data`. Новая версия при следующем запуске снова предложит
свою автоматическую миграцию; выясните причину сбоя до её повторного применения.

## Приёмка этапа 3.1

- [ ] Существующие А/B/C, ID, планы и события доступны в «Строительном проекте».
- [ ] Создаётся «Школа» с «Учебным» и «Спортивным» корпусами, без автоматических этажей.
- [ ] Дублированный код корпуса отменяет создание объекта целиком.
- [ ] В разных объектах допустимы одинаковые коды корпусов и общий код работы.
- [ ] Можно добавить этаж, работу, план/норму и утвердить V1.
- [ ] Черновая работа скрыта в выполнении; утверждённая появляется автоматически.
- [ ] План 1000, факт 600, подтверждение 450 дают 60% и 45%.
- [ ] Переключение меняет показатели, корпуса, версии и журналы.
- [ ] Номер V1 начинается независимо для каждого объекта/направления.
- [ ] Переименование корпуса сохраняет этажи, позиции и историю.
- [ ] Архивирование и восстановление не удаляют данные.
- [ ] Исторический срез учитывает дату выполнения и отсечение знаний.
- [ ] Исключённая работа остаётся в журнале, но скрыта в текущих плановых работах.
- [ ] После перезапуска оба объекта доступны без потери данных.
- [ ] Обновление и обычная работа выполняются офлайн после установки зависимостей.

## Ограничения

- Рабочее пространство сохраняется в подписанной сессии браузера. После нового
  процесса сервера/смены порта сессия начинается заново; объект можно выбрать повторно.
  Данные объектов при этом остаются в SQLite.
- Нет многопользовательских ролей и отдельной сущности подписания отчёта.
- Неверная новая ведомость с видимыми событиями вне её состава по прежним правилам
  возвращает INVALID/MISSING_PLAN_LINE. Старый план остаётся доступен для истории.
- Число объектов/корпусов не ограничено бизнес-логикой, но размер одной веб-формы
  ограничен существующим лимитом 128 КиБ; множество корпусов можно добавлять поэтапно.
- Удаление записей истории, автоматическое изменение норм, `.app`, Windows и этап 3.2
  не реализованы. Объектную область нельзя подменять ручным SQL в рабочем файле.
