# Этап 4.3 — реализация

Основание: полное ТЗ пользователя, рабочая копия без сброса и push.

- Зафиксировать исходные SHA/Git/схему, прогнать регрессию.
- 011_labor_productivity.sql: только новые append-only операции, ревизии
  распределений часов и атрибуций объёмов. Старые 001–010 не менять.
- Часы: наночасы как в табеле, FK на неизменяемую утверждённую запись;
  последние утверждённые версии по времени знания; проверка общего распределения
  employee/date внутри объекта в BEGIN IMMEDIATE; персональная детализация bulk.
- Объёмы: явный исполнитель, FK на положительный корневой факт; доступность
  учитывает цепочку корректировок. Полные ревизии назначения, optimistic revision,
  ключ операции, причины исправлений. Не создавать факты/часы при распределении.
- Пакетная аналитическая проекция с Decimal, отдельным режимом подтверждения
  (исполнитель неизвестен без прямой связи), календарной средней численностью,
  полнотой и конфликтами. Конфликтные группы исключаются из окончательных KPI.
- Общая навигация, формы распределения/атрибуции с просмотром, история,
  фильтры и XLSX через имеющийся writer. Пагинация реестров на сервере.
- Тесты, средний временный профиль, Chromium 1366×768, документация и Mac сценарий.

Решение: норматив фиксируется ссылкой на утверждённую версию при распределении
и атрибуции; для общего отчёта можно явно выбрать утверждённую версию плана.
При отсутствии явного выбора применяется версия, действовавшая на бизнес-дату
события. Исполнитель никогда не выводится из наряда. Период — включительно;
средняя численность учитывает все календарные дни диапазона, включая нулевые.

Независимую веб/XLSX часть выполняет агент; ядро хранения и расчётов — основной.
