# ПЛАНКТОН. Учёт рабочего времени — Windows Portable Build Kit W1.0

## Текущий статус

Подготовлена воспроизводимая **PyInstaller onedir** сборка существующего
Flask-приложения. Текущая среда — Linux, доступной Windows-среды нет.
**Windows EXE и готовый Portable ZIP здесь не собраны и на Windows не проверены.**
Новый архив `PlanktonTime-Windows-BuildKit.zip` содержит исходники, инструкции и
скрипты сборки с новым брендом. Это не архив для запуска без Python.

Исходники включают этапы 4.3–4.5 и ребрендинг. Состояние частичного 4.2.1 и его
ограничения сохранены в `stage421_results.md` и `stage421_performance.md`.
Ребрендинг не завершает нагрузочный этап и не меняет расчёты физической готовности.

## Как получить настоящий Portable ZIP

На компьютере сборщика Windows 10/11 x64 установить CPython 3.13 x64
(для повторяемой среды рекомендуется 3.13.12), распаковать Build Kit и запустить
`BUILD_WINDOWS.cmd`. Или в PowerShell из корня:

```powershell
& .\packaging\windows\build.ps1
```

Первое создание среды сборки загружает закреплённые зависимости из PyPI.
Для полностью офлайн-сборки заранее подготовить соответствующие Windows wheels
и передать `-Wheelhouse 'D:\wheels'`. Приложение после сборки не использует pip,
не загружает зависимости и не требует Python или интернета на машине пользователя.

Скрипт выполняет регрессию, явно отмечая macOS Bash-проверки как пропущенные на
Windows, собирает EXE, проверяет Windows PE x64 и ресурсы, запускает EXE на временном
профиле и только затем создаёт **`dist/PlanktonTime-Windows-x64.zip`**.
При ошибке любого шага готовая поставка не объявляется успешной. Старые архивы
не перезаписываются. GitHub, GitHub Actions и публикация не используются.

## Архитектура и пути

Единый код: браузер → Waitress → существующий Flask/Jinja2 → расчётное ядро → SQLite.
Windows-модули изолированы в `app/portable`, `windows_launcher.py`,
`tools/windows`, `packaging/windows`. macOS `start.command` и прежний сервер сохранены.
Ребрендинг не добавляет таблиц и миграций. Включены существующие миграции 001–013.

В настоящем onedir архиве:

```text
PlanktonTime/
  PlanktonTime.exe
  _internal/                  # runtime, templates, static, migrations, Excel templates
  data/                       # первая рабочая база создаётся при первом запуске
  backups/
  exports/
  logs/
  README.txt
  VERSION.txt
  BUILD_INFO.json
```

База: `data/construction_progress.sqlite3` **рядом с EXE**, вне `_internal`.
Пути определяются по EXE и ресурсам, независимо от текущего рабочего каталога.
Поддержка пробелов/Unicode проверена на уровне Linux файловых тестов; Windows
NTFS, кириллица, длинные пути и выбор файлов требуют нативной проверки.
Не предполагается обход системного ограничения Windows MAX_PATH.

Для независимого профиля:

```powershell
& .\PlanktonTime.exe --data-dir "$env:USERPROFILE\Documents\Личный профиль"
```

Всегда использовать один и тот же `--data-dir`, включая резервирование и обновление.
Не хранить данные в Program Files, общедоступной папке или внутри `_internal`.
При отсутствии прав записи launcher сообщает об ошибке и не подбирает другой
профиль автоматически. В режиме исходников `--data-dir` обязателен, чтобы случайно
не обновить базу репозитория. Экспорт через браузер сохраняется по настройкам
загрузок браузера; каталог `exports` не переопределяет их.

## Запуск, повторный запуск и завершение

Распаковать всю portable-папку и открыть EXE. Не запускать EXE внутри ZIP и не
переносить отдельно от `_internal`. Сервер резервирует настоящий сокет на
**127.0.0.1:0**, передаёт его Waitress и получает фактически назначенный порт.
Сканирования свободных портов с последующим отдельным bind нет.
Debug/reloader отключены; Host, Origin, CSRF и CSP остаются действующими.

Браузер открывается после аутентифицированной проверки готовности приложения.
При неудаче URL выводится в консоль. Секреты не передаются в URL. Номер порта
может изменяться при новом запуске; нужно использовать актуальный адрес.

На профиль удерживается блокировка ОС: `msvcrt` на Windows, `flock` в Linux-тестах.
Второй процесс не открывает базу для миграций: сначала проверяет живой сервер
через случайный challenge/HMAC на loopback и открывает существующий адрес.
Один устаревший lock-файл или повторно использованный PID не являются признаком
работающего сервера. При занятой блокировке и недоступном сервере второй сервер
не создаётся. Разные реальные копии базы в разных профилях — разные приложения.
Не запускать один файл базы сторонними средствами в обход этого launcher.

Завершать существующей кнопкой **«Завершить работу»** (POST + Origin + session CSRF)
или Ctrl+C в консоли. Закрытие вкладки не останавливает приложение.
Контроллер прекращает приём новых операций, ожидает активные WSGI-операции и
закрытие соединений, затем останавливает Waitress и освобождает блокировку.
Не применять принудительное завершение процесса и закрытие консоли во время
записи. ОС может прервать процесс при выключении/принудительном закрытии;
гарантии завершения произвольной операции в таком случае нет.

## Первый запуск и обновление SQLite

При отсутствии базы используется действующий `initialize`: создаются схема и
справочники приложения. Работники, события, наряды и объёмы демонстрацией не
заполняются. Традиционные стартовые корпуса/коды остаются частью существующей
инициализации и не являются перенесёнными пользовательскими данными.

Перед изменением существующей схемы:

1. Проверяются `integrity_check`, `foreign_key_check`, история миграций и совместимость.
2. В `backups` создаётся новая уникальная проверенная копия **SQLite Backup API**.
3. Вся цепочка обновления пробуется на отдельной копии внутри временного каталога.
4. При успехе применяются существующие транзакционные миграции к исходной базе.
5. Целостность проверяется повторно; только после успеха запускается HTTP-сервер.

Искусственная SQL-ошибка на пробном этапе сохраняет исходный файл побайтно и
оставляет проверенную копию. Если ошибка диска возникнет во время реального
применения, запуск прекращается: каждая прежняя миграция атомарна, но вся цепочка
не является одной общей транзакцией. Автоматической замены/отката пользовательского
файла из резервной копии нет; путь копии показывается пользователю.
Штатный механизм может дополнительно сохранять копию в `data/backups`.

## Резервное копирование и перенос между платформами

После завершения приложения:

```powershell
& .\PlanktonTime.exe --backup
# Если профиль внешний:
& .\PlanktonTime.exe --data-dir 'D:\Личный профиль' --backup
```

Работающее приложение необходимо остановить: второй процесс резервирования
отклоняется. Созданная копия проверяется, существующие копии не перезаписываются.
Не копировать открытую SQLite-базу обычным копированием файла как основной backup.

База имеет общую с macOS схему. Для переноса завершить приложение на обеих
платформах, создать проверенный backup, перенести его как базу в **новый профиль**,
проверить совместимость схемы. Не понижать версию приложения для базы с новой схемой.
Не заменять работающую базу и учитывать WAL/journal файлы при аварийном завершении.

Обновление без перемещения данных: остановить прежний EXE → создать backup его
командой `--backup` → распаковать новый ZIP во временный каталог → заменить только
EXE, `_internal`, README/VERSION/BUILD_INFO в **прежней папке установки** →
запустить `PlanktonTime.exe` из прежней папки → проверить объекты и базу.
Не заменять каталоги `data`, `backups`, `exports`, `logs` и файлы профиля.
Название прежней папки менять не требуется. При внешнем профиле сохранить
**тот же** `--data-dir` в ярлыке и командах диагностики/резервирования.
Не запускать EXE из нового временного каталога: по умолчанию это другой профиль.
Не брать пустую базу из другой установки. Автоматического переноса/переименования
данных при ребрендинге нет. Подробнее: [совместимость](rebranding_plankton.md).

## Диагностика и защита данных

```powershell
& .\PlanktonTime.exe --diagnose
```

Диагностика read-only: версии приложения/Python/SQLite/Waitress, пути, состояние
каталогов, список миграций, целостность и ресурсы. ФИО и строки персонала не выводятся.
`logs/application.log` хранит время, уровень, безопасный код и класс ошибки,
без тел форм, значений ячеек и traceback. Ротация: 1 MiB × 4 файла.
Неизвестная ошибка веб-приложения отображается понятным сообщением без traceback.

Localhost не заменяет авторизацию. Другие программы в той же учётной записи
могут читать доступные пользователю файлы и токен экземпляра. Шифрования базы,
пользователей/ролей и юридически значимых подписей не добавлено. Защита реальных
персональных данных требует защищённой учётной записи Windows, прав NTFS,
защиты компьютера и резервных копий. EXE пока не подписан сертификатом.

## Обязательная ручная Windows-приёмка

Записать Windows version/build/x64, Edge/Chrome и характеристики оборудования.
На машине без Python, без прав администратора, затем с отключённым интернетом:

- Распаковать ZIP в папку с пробелами и кириллицей; проверить первый и повторный
  запуск, браузер, Ctrl+C и кнопку завершения, отсутствие второго сервера.
- Проверить создание/переключение объектов, ведомость, факт **без наряда**,
  подтверждение, корректировки и исторический срез.
- Создать и распечатать наряд A4 landscape; проверить кириллицу и масштаб.
- Пройти пятишаговый импорт работников, выбрать файл с кириллическим именем.
- Создать/заполнить/утвердить табель, открыть корректирующую и исходную версии.
- Скачать/открыть Excel аналитики и табеля; проверить импорт и числовые значения.
- Остановить/запустить, проверить сохранность; выполнить backup и обновление.
- Измерить запуск, dashboard, ведомость, табель, Excel и RAM на малом профиле.
  С Linux-результатами 4.2.1 сравнивать с учётом различий оборудования.

Нативная и браузерная приёмка в текущей среде не выполнены. Успешная генерация
Build Kit сама по себе не выполняет критерии готовности Windows Portable.
