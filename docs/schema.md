# SQLite: схема этапов 1–3.3

Источник истины — `migrations/001_initial.sql` — `007_work_order_events.sql`; миграции 001–006 сохранены без изменений.
Схема не использует нативные расширения и пригодна для macOS/Windows.

| Таблица | Поля | Ключевые ограничения |
| --- | --- | --- |
| `projects` | id, name, code, description, status, created_at, updated_at | PK id, UNIQUE code, active/archived, обязательные название/код |
| `buildings` | id, project_id, code, name, sort_order, status | PK id, FK project, UNIQUE(project_id,code), active/archived, целый порядок |
| `floors` | id, building_id, floor_code, sort_order | FK building, UNIQUE(building_id,floor_code), UNIQUE(id,building_id), целый порядок |
| `work_catalog` | id, code, work_type, element, name, unit | UNIQUE code, непустые классификаторы и единица |
| `work_items` | id, building_id, floor_id, catalog_id, discipline | FK building/catalog; составной FK(floor_id,building_id); UNIQUE(building_id,floor_id,catalog_id,discipline) |
| `plan_versions` | id, project_id, discipline, version_no, status, approved_at, created_at | FK project, UNIQUE(project_id,discipline,version_no), DRAFT/APPROVED, согласованность статуса и времени |
| `plan_lines` | id, plan_version_id, work_item_id, planned_quantity, labor_norm, **unit** | FK version/item, UNIQUE(version,item), неотрицательные канонические Decimal TEXT, norm может быть NULL только до утверждения |
| `fact_events` | id, work_item_id, quantity_delta, work_date, recorded_at, comment, correction_of_id, **event_key, unit, source_type, work_order_line_id, overrun_reason** | FK item/self/order line, UNIQUE event_key, ненулевая подписанная Decimal TEXT, неизменяемость, необязательная строка наряда |
| `confirmation_events` | id, work_item_id, quantity_delta, confirmed_date, recorded_at, document_ref, correction_of_id, **event_key, unit, comment, source_type, work_order_line_id** | FK item/self/order line, UNIQUE event_key, обязательный документ, неизменяемость, необязательная строка наряда |
| `audit_log` | id, entity_type, entity_id, operation, recorded_at, details | INSERT/UPDATE/DELETE, неизменяемость; details содержит OLD/NEW значения в SQL-литералах |
| `schema_migrations` | name, applied_at | PK name, служебная история применения миграций |

Добавленные к заданию `unit` — снимки единицы для контроля совместимости;
`event_key` — стабильный ключ исходного события для защиты от повторного импорта.
Без этих полей невозможно надёжно различать несовместимые единицы и повторы регистрации.
Этап 2 добавил отдельный `confirmation_events.comment`, не заменяющий документ-основание.
Для существующих записей он получает пустую строку; исходные даты, объёмы и ссылки сохраняются.

`discipline`: `DESIGN` (проектирование) или `CONSTRUCTION` (СМР).
В одной версии плана может быть только одна дисциплина; триггер проверяет каждую строку.
Смешанный показатель проекта намеренно не определён.

`planned_quantity`, `labor_norm`: десятичные строки без знака, экспоненты,
ведущих нулей и дробных хвостовых нулей. Например: `0`, `1000`, `0.8`.
`quantity_delta`: тот же формат с необязательным `-`; `0` и `-0` запрещены для события.
Предел входа: 18 целых и 9 дробных разрядов. Нулевые объёмы/нормы допустимы
в черновике для подготовки данных, но препятствуют утверждению и достоверному расчёту.

Даты работ и подтверждения: `YYYY-MM-DD`, проверяются календарная корректность и формат.
Даты регистрации/создания/утверждения: фиксированный UTC
`YYYY-MM-DDTHH:MM:SS.ffffffZ`, что обеспечивает точное лексикографическое сравнение.
Служебный `schema_migrations.applied_at` использует стандартную UTC-метку SQLite.
Аудит записывает фактический момент операции БД; `recorded_at` события при доверенном
импорте может представлять более ранний момент регистрации в источнике.

Триггеры:

- Запрещают UPDATE/DELETE событий и аудита; явные коллизионные проверки блокируют `REPLACE`.
- Защищают утверждённые версии и их строки от всех изменений и замены.
- Запрещают прямое создание утверждённой версии и утверждение пустого/неполного плана.
- Проверяют соответствие дисциплины и единицы позиции/плана/события.
- Проверяют принадлежность корректировки той же позиции и её хронологию.
- Фиксируют вставки, изменения и удаления основных сущностей в аудите атомарно.
- Защищают используемую классификацию от изменения, предотвращая дрейф исторических групп.

В миграции 003 защита этажа уточнена: используемый этаж можно переставлять через
`sort_order`, но нельзя менять `id`, `building_id` и `floor_code`. Для кодификатора
защита используемых записей сохранена. Аудит новой записи подтверждения включает
как документ, так и комментарий. Новых учётных таблиц веб-интерфейс не создаёт.

Индексы журналов: `(work_item_id, business_date, recorded_at)`;
плана: `(project_id,discipline,status,approved_at,version_no)`. Все FK действуют без каскадного удаления.
`PRAGMA foreign_keys=ON`, `recursive_triggers=ON`, `busy_timeout=5000` задаются на каждом
соединении приложения. Журнал транзакций — стандартный rollback journal SQLite.

Межстрочные ограничения `SUM(confirmed) <= SUM(actual)` и неотрицательность накоплений
проверяются репозиторием в Decimal под `BEGIN IMMEDIATE`, по всем историческим границам.
Они не выражены в SQL через `SUM(TEXT)`, поскольку SQLite преобразовала бы строки
в двоичные числа. Расчётное ядро повторно проверяет их для выбранного среза.
Записывать производственные данные следует через репозитории.

## Объектная область и миграция 004

`project_id` хранится только в `buildings` и `plan_versions`. Этаж → корпус → объект;
позиция → корпус → объект; события → позиция. Кодификатор общий. Триггеры строк
плана запрещают ссылки между объектами, дополнительно к существующим проверкам
дисциплины и единицы. Перенос корпуса или версии в другой объект запрещён.
Названия/коды/порядок корпуса разрешено менять с сохранением `building_id`.

Глобальные UNIQUE кода корпуса и номера версии заменены составными. Для этого
таблицы пересоздаются под `BEGIN IMMEDIATE` через новые временные таблицы, без
`REPLACE`. Перенос сохраняет все исходные поля и ID. Контроль FK временно отключается
вне транзакции только для пересоздания, затем FK и `integrity_check` проверяются
до COMMIT; настройки всегда восстанавливаются, включая ошибку. Индексы и триггеры
восстанавливаются. Приложение проверяет количество и SHA-256 содержимого исходных
колонок всех учётных таблиц и аудита до/после DDL.

Перед обновлением существующего файла используется SQLite Backup API; копия
проверяется и сохраняется в соседнем каталоге `backups`. При ошибке 004 её изменения
откатываются, копия сохраняется. Успешные предыдущие миграции остаются применёнными.
Повторный запуск пропускает 004 и не создаёт новый объект или повторные корпуса.
Свежая установка получает прежние А/B/C один раз; новые объекты — только указанные
пользователем корпуса. Физического удаления объектов в API нет: используется архив.

Удаление свободного **корпуса** выполняется репозиторием под `BEGIN IMMEDIATE` после
проверки всех входящих связей к корпусу и его этажам. При наличии учётных позиций
или иных зависимостей удаление запрещено; доступно архивирование через существующее
`buildings.status`. Пустые этажи удаляются явно только при отдельном согласии.
Аудит не удаляется. Новая миграция для этого дополнения не требуется.
Подробнее: [управление корпусами](building_management.md).

## Источник событий, миграция 005

Аддитивные `fact_events.source_type` и `confirmation_events.source_type` — непустой
идентификатор из `[a-z0-9_]` длиной до 80. Старым строкам назначается `legacy`:
их источник прежде не фиксировался. Новый ручной ввод получает `manual`, включая
корректировки. Источник включён в аудит вставки. Сами события остаются append-only.
Новых таблиц и обязательной ссылки на наряд нет. Формулы и колонки Decimal не меняются.
Перед 005 существующая база копируется через Backup API в `backups/before-event-flow-*.sqlite3`.
Улучшение очереди не требует дополнительных сохранённых итогов: списки производны
от позиций, строк выбранного плана и обоих журналов с фильтрами дат/знаний/объекта.

## Документы и персонал, миграция 006

Добавлены `contractors`, `specialties`, `employees`, `work_orders`,
`work_order_sequences`, `work_order_lines`, `work_order_crew`,
`work_order_crew_members`, `work_order_approvals`, `work_order_status_history`.
Справочники организаций/работников и шапки нарядов имеют область `project_id`;
специальности общие. Бригады, строки и история получают объект через наряд.

Строка задания ссылается на `work_items.id` и составной ключ строки плана.
План смены — точный канонический Decimal TEXT, не заменяющий `plan_lines`.
Снимки шапки, названий, единиц, расположения и бригады фиксируются при выдаче.
JSON хранится как TEXT и обрабатывается Python без SQLite JSON1.

Счётчик объекта, уникальность `(project_id,order_number)` и `BEGIN IMMEDIATE`
обеспечивают последовательную выдачу номеров. Черновики номера не занимают,
отменённые номера не используются повторно. Допустимы только выдача черновика
и отмена черновика/выданного документа с основанием. Выданные строки/снимки,
регистрация выдачи и история защищены триггерами; записи новых сущностей
включены в существующий аудит. FK не имеют каскадного удаления.

Перед 006 существующая база копируется через SQLite Backup API. Миграция аддитивна
и применяется одной транзакцией с проверкой исходных колонок, количеств строк,
SHA-256, integrity_check и FK перед COMMIT. Исходные расчётные таблицы и события
не изменяются. Подробная [схема, инварианты и обновление](work_orders.md).

## Аддитивное расширение 007: события нарядов и решения

`fact_events.work_order_line_id` и `confirmation_events.work_order_line_id` —
необязательные FK на `work_order_lines.id` без каскадного удаления.
`work_order_id` получается через строку и не дублируется в событиях.
Старые записи получают NULL; `source_type`, даты, дельты, ID и коррекции сохраняются.
`fact_events.overrun_reason` хранит причину отдельно разрешённого превышения задания.
`work_orders.workflow_reason` передаёт основание текущего перехода в прежнюю историю.

| Новая таблица | Поля | Ограничения |
| --- | --- | --- |
| `work_order_workflow_actions` | id, work_order_id, status_history_id, action, employee_id, employee_name_snapshot, performed_at, comment, snapshot, event_signature, event_key | FK order/history/employee; action submitted/accepted/closed; UNIQUE event_key; только добавление |
| `work_order_line_reviews` | id, action_id, work_order_line_id, checked, comment | FK action/line; UNIQUE(action_id,work_order_line_id); checked 0/1; только добавление |

`work_order_approvals` из 006 ограничена одним согласованием выдачи на документ и
CHECK `action='issued'`. Чтобы сохранить её строки, схему и ID без пересоздания,
новые решения добавлены отдельным расширением существующего аудита. Карточка
объединяет выдачу, новые решения и прежнюю `work_order_status_history`. Повторная
проверка в `accepted` создаёт новое решение без дублирования перехода статуса.
`snapshot` — JSON со строковыми Decimal, на момент сдачи/проверки/закрытия;
это аудиторский снимок, не источник выполнения для расчётного ядра.
`event_signature` — SHA-256 набора связанных событий выбранного среза для проверки
изменений между показом формы и сохранением, а также после проверки/закрытия.

Индексы событий используют `(work_order_line_id, business_date, recorded_at)`.
Триггеры защищают принадлежность строки работе и объекту, выданный номер, единицу,
дату регистрации после выдачи и допустимые статусы. Коррекция обязана сохранить
ссылку исходного события, включая NULL. Источник `work_order` требует ссылки;
`manual` может быть как со ссылкой, так и без неё. Первый обычный положительный
факт переводит только `issued → in_progress` в одной транзакции с записью события.
Обычные подтверждения и независимый факт статус не изменяют.

Репозиторий под `BEGIN IMMEDIATE` дополнительно проверяет действующий план,
хронологию решений, точные общие и связанные накопления, превышение задания,
доступный остаток подтверждения и исторические ограничения. Связанное подтверждение
может превышать связанный факт данного наряда, но не общий факт работы. FK и
триггеры не заменяют точные межстрочные проверки Decimal; прямой SQL не является API.
Новых таблиц независимого факта или подтверждения наряда нет.

Миграция 007 использует ALTER TABLE ADD COLUMN и новые таблицы/триггеры.
Существующие таблицы не пересоздаются. До обновления постоянной базы через SQLite
Backup API создаётся проверенная копия, затем миграция целиком выполняется под
`BEGIN IMMEDIATE`. Исходные столбцы всех пользовательских таблиц, включая документы,
персонал, счётчики и аудит, сверяются по количествам и SHA-256, затем проверяются
`integrity_check` и внешние ключи. Ошибка откатывает и данные, и DDL, и маркер;
повторный запуск не создаёт дубли. Предыдущие SQL-файлы 001–006 неизменны.
